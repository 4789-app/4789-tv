# 4789 TV client — UI and performance audit

Date: 2026-09-21. Scope: `app/src/main/java/com/fourseveneightnine/tv/client/**` and
`client-data/.../images/**`. Analysis only. Nothing was edited and the box was not touched.

Contract read: `docs/design/TV_DESIGN_SPEC.md`, `docs/TV_APP_REBUILD_PLAN.md` §7, §7.4, §9, §12.
Screencaps read: `p7-row`, `p7-detail`, `p7-play`, `p6-home`, `p1-search`, `t2-discover`,
`p9-discover`, `p9-chrome`.

Measured baseline on the onn 4K Pro, 24 presses along a Home row: 50% janky frames, 53 ms median.
Compose stage median 6 ms, p90 45 ms. Draw record median 3 ms, p90 17 ms. GPU median 13 ms,
p90 27 ms. The GPU is fill-rate bound. The budget in plan §9 is 3% janky, median 24 ms.

One caveat before any fix. The install command in plan §11 installs `sideload/debug`, and
`app/build.gradle.kts` turns R8 on for `release` only. A debug Compose build runs without
optimisation. Re-measure on `sideloadRelease` first, or half the compose-stage number is the build.

## 2. Findings in detail

### F01 — "See all" leaves focus on the hidden screen (P0)

`CatalogGridOverlay` draws an opaque full-screen box over Home. It never calls `requestFocus`.
The Home rows below it stay composed and stay focusable. The ring is therefore on a card the
viewer cannot see, and the D-pad scrolls a hidden row.

Fix. Add a `FocusRequester` on a node the overlay always composes. The title `Text` wrapped in a
focusable will do, or the grid container itself. Request it from
`LaunchedEffect(catalog.catalogId)`. Then block the screen behind it. In `HomeScreen.kt:200`, put
`Modifier.focusProperties { canFocus = false }` on the content `Column` while `seeAll != null`.
Also set `shell.overlayVisible = true` while the overlay is up.

Effect: the ring appears on the grid. The remote works.

### F02 — Removing a row makes the posters jump (P0)

`HomePlan.applyResult` returns `null` for a row whose result is empty, and `applyFailure` filters
the row out. Both delete the `LazyColumn` item. Every row below moves up by one row block, which is
410 px on a poster row. Twelve catalogs answer over about eight seconds. Some of them answer
empty, so the jump happens more than once on every cold start.

Spec §3.7 states the rule the code breaks: "A row that answers empty is removed. If focus is
inside or below that row, the removal waits until focus moves above it." Spec §3.6 adds "190 ms
slide up, only when focus is above it".

Fix, three parts.
1. Add `val removed: Boolean` to `HomeRow.Posters`. Set it instead of returning `null`. Skip
   drawing the row only when it sits above the focused row.
2. Track the focused row index in `HomeScreen` and pass it to the view model. The removal can then
   wait. The simplest version that stops every jump: never remove a row the screen has drawn.
   Draw it as a zero-height item and drop it on the next screen entry.
3. Add `Modifier.animateItem()` to the `LazyColumn` item in `ShelfBand` so any removal that is
   allowed slides rather than cuts.

Effect: the band stops moving under the ring. This is the largest single cause of the owner's
"flickering of posters up and down".

### F03 — The rescue net scrolls the band to the top (P0)

`AppRoot.kt:185` waits 900 ms with nothing focused, then calls `shell.restoreContentFocus`.
Home's version (`HomeScreen.kt:120-124`) calls `rowsFocus.requestFocus()` on the `LazyColumn`.
The column has `focusRestorer()`. After a row removal the saved child is gone. Focus lands on the
first item and the column scrolls back to row 1.

This runs together with F02: delete the focused row, focus dies, 900 ms later the whole band
snaps to the top. That is the second half of the up-and-down movement the owner reports.

Fix. Have `restoreContentFocus` restore the last focused row index, not the list head. Keep the
index in a plain `intArrayOf(0)` written by `TvCardRow`'s `onFocusChanged`, and call
`listState.scrollToItem(index)` before requesting focus. Fixing F02 removes most of the trigger.

### F04 — Late rows push the whole band down (P1)

`HomePlan.rows` puts Continue first and Collections second, and both come from Room flows that
emit after the catalogs have painted. Inserting at index 0 moves every row down 291 or 326 px.

Fix. Plan both slots up front. Emit `HomeRow.Continue(emptyList())` and
`HomeRow.Collections(emptyList())` as zero-height reserved items from the first publish. Let them
grow in place. The change is small: keep the key in the list, draw nothing while the item list is
empty, and stay unfocusable.

### F05 — A blank hero with a dead Play button (P1)

`p6-home.png` shows the whole 524 px hero band empty except an orange Play button.

Two lines cause it. `HomeFolderCardView`'s `onFocused` passes `(null, null)`
(`HomeScreen.kt:319`), as does `SeeAllCard` (`:337`). The settle flow then returns early on null
(`HomeScreen.kt:112`), so `settledCard` is never written. On a box whose first row is Collections
the hero never gets a card at all. And `onAction` is `settledCard.value?.let { ... }`
(`HomeScreen.kt:207`), so OK on the button does nothing. Spec §3.9.15 forbids exactly that.

Fix. On a folder or See-all card, keep the last settled card. Do not clear it. Disable the hero
button when `settledCard.value == null`: `TvButton(enabled = settledCard.value != null)`.
Better still for a folder row: show the folder name and count in the hero slot.

### F06 — Focus scale recomposes the card every frame (P1)

```kotlin
val value by animateFloatAsState(...)   // Focus.kt:73
return this.scale(value)                // Focus.kt:81
```

`tvFocusScale` is a composable modifier, so it is inlined into the card's composition scope.
Reading `value` there invalidates that scope on every animation frame. Two cards animate per key
press, so one press costs roughly 20 recompositions of a card subtree that contains an
`AsyncImage`, a `Text` and badges. This is the compose stage the p90 of 45 ms is made of.

Fix.

```kotlin
val anim = remember { Animatable(1f) }
LaunchedEffect(focused, reduceMotion) {
    anim.animateTo(if (focused) target else 1f, tween(if (reduceMotion) 0 else FocusScaleMillis, easing = Std))
}
return this.graphicsLayer { scaleX = anim.value; scaleY = anim.value }
```

The lambda form of `graphicsLayer` reads the state in the draw phase, so composition and layout are
never invalidated.

Effect: cuts the compose stage on a focus move. Target: p90 under 12 ms.

### F07 — The skeleton sweep is the most expensive thing on a cold start (P1)

`Skeleton` with `sweep = true` calls `rememberInfiniteTransition` per block
(`Components.kt:575`) and builds a `Brush.horizontalGradient` from the animated value in the
composable body (`:589`). Every block therefore recomposes at 60 fps and allocates a brush and a
colour-stop array each time.

Cold start draws: three sweeping blocks in `HomeHeroSkeleton`, seven in the first
`HomeShelfSkeleton`, and seven more in each `ShelfSkeletonRow` where `index < 2`
(`HomeScreen.kt:362`). That is up to 17 independent infinite animations, 17 recompositions per
frame, and about 1.4 million pixels of gradient fill per frame on a fill-bound GPU.

Fix.
1. Hoist one `rememberInfiniteTransition` to the screen and pass the phase down, or better, expose
   the sweep as `Modifier.drawWithCache { onDrawBehind { ... } }` that reads the animated value
   inside the draw lambda and caches the brush across frames.
2. Sweep one block per screen, not seven. Spec §15.4 says the sweep runs on the hero and the first
   row, which was read as "every block in the first row".

Effect: removes 17 per-frame recompositions and most of the gradient fill during the first two
seconds. This is the cold-start jank in `p6-home.png`.

### F08 — Discover re-lays-out the whole grid during the band collapse (P1)

`val bandTop by animateDpAsState(...)` at `DiscoverScreen.kt:116` is read at `:185` inside
`Modifier.offset(y = bandTop)`. The `Dp` overload of `offset` takes its value at composition, so
every frame of the 180 ms tween recomposes the screen and re-measures a `LazyVerticalGrid` holding
thirty-plus cells.

Fix. Use the lambda overload:

```kotlin
val bandTopPx by animateFloatAsState(if (collapsed) 72f else 162f, ...)
Box(Modifier.fillMaxSize().offset { IntOffset(0, bandTopPx.roundToInt()) })
```

with the value converted through `LocalDensity` once. Effect: the band collapse costs draw only.

### F09 — The Discover grid is taller than the screen (P1)

`Box(Modifier.fillMaxSize().offset(y = bandTop))` gives the box the full 1026 px of the padded
parent and then pushes it down 162 px. Its bottom edge is 162 px below the panel.

Two consequences. The grid composes about six cells that can never be seen, which is six extra
poster fetches and decodes. And `bringIntoView` treats a cell in that strip as already visible, so
DOWN onto the bottom row does not scroll and the ring lands off-screen.

Fix: `Box(Modifier.fillMaxWidth().weight(1f))` inside a `Column`, or
`Modifier.fillMaxSize().padding(top = bandTop)` so the height shrinks with the offset.

### F10 — The Discover grid jumps when data lands (P1)

`GridSkeleton` uses `Spacer(GridRowGap + 46.dp)` (`DiscoverGrid.kt:215`), a pitch of 428 px.
`GridCell` measures 354 + 10 + 28 + 2 + 26 = 420, plus the 28 px gap, so the real pitch is 448 px.
The spec says 410 and 438. Three different numbers.

Fix. Set the cell text heights explicitly — `Modifier.height(24.dp)` on the title and
`Modifier.height(22.dp)` on the meta — so a cell is 410, and change the skeleton spacer to
`GridRowGap + 56.dp`. All three then agree at a 438 px pitch.

### F11 — Detail backdrop overdraw (P1)

`Backdrop` draws, every frame, in this order: a 1920 x 1080 image, a 1560 x 1080 horizontal
gradient and a 1920 x 380 vertical gradient. That is about 4.5 million pixels written on a
2.07 million pixel panel, before the hero, the poster or a single rail.

Home already solved this: `HomeHero.kt:58-63` explains the same measurement and cut the backdrop to
1140 x 620. Detail never got the change.

Fix. Draw the image and both gradients in one `Modifier.drawWithCache` on a single node, so the
gradients are `drawRect` calls into the same layer with cached brushes. Then shrink the left
gradient to the width it is still visible across — it is fully opaque by x 700, so a 700 px box plus
a flat `canvas` fill to its left saves 860 px of blending per row.

Effect: cuts the GPU stage on Detail. Target: median under 8 ms.

### F12 — The hero text crossfade blends two full bands (P1)

`Crossfade(targetState = settled)` at `HomeHero.kt:120` wraps each child in a graphics layer with
an alpha. Both children are `Box(Modifier.fillMaxSize())` inside a 1700 x 524 band. After every
settle the GPU composites two off-screen layers of 890,000 pixels for 190 ms.

Fix. Crossfade only the parts that change, at their real sizes: the logo box (520 x 160), the meta
line and the synopsis. Or drop `Crossfade` and animate one alpha on a single `HeroText`, re-keying
the content at the alpha's low point.

### F13 and F14 — Posters flash their titles and fade in again (P1)

`TvArtwork` keeps `painted` in `remember(request.url)` (`Components.kt:677`). A `LazyRow` item that
scrolls out of the composed window loses that `remember`. When it comes back, `painted` is false,
so the title text draws over the placeholder until `onSuccess` fires. The `onSuccess` write then
recomposes the card.

The fade underneath it: the loader sets `crossfade(190)` globally (`ImageLoaderFactory.kt:69`) and
the memory cache is 15% of heap (`:34`). Coil skips the crossfade for a memory-cache hit but runs

twice re-decodes from disk and fades in again.

1. Drive the title from Coil's own state instead of a remembered boolean:
   `SubcomposeAsyncImage`, or `AsyncImage(..., placeholder = ...)`, or keep the flag in a
   `rememberSaveable`-style map keyed by url and held by the row, not the item.
2. Set `crossfade(false)` on poster requests and keep the 190 ms fade for the backdrop and the
   hero logo only. `PosterRequest.toImageRequest` already branches on width
   (`ImageLoaderFactory.kt:92`); add the crossfade choice to the same branch.
3. Raise `MEMORY_CACHE_PERCENT` from 0.15 to 0.25, and prefer `RGB_565` for every poster rather
   than only on a low-RAM box. A 342 x 513 poster at 565 is 351 KB, so 0.25 of a 192 MB heap holds
   about 130 posters — roughly four full rows in each direction.

Effect: this is the owner's "flickering of posters", the part that is not vertical movement.

the `NavHost` with nothing between them. `p9-discover.png` was captured mid-playback and shows

### "Flickering of posters up and down, a lot"

Two separate faults, both reproducible from the code.

**Vertical movement.** F02, F03 and F04 form one chain. A catalog answers empty, the row is deleted
(`HomeViewModel.kt:217`, `:224`), every row below jumps up 410 px. If the ring was on that row,
focus dies. 900 ms later the shell's rescue net (`AppRoot.kt:185-195`) calls
`shell.restoreContentFocus`, which requests the `LazyColumn` head (`HomeScreen.kt:121`), and the
band scrolls to the top. Separately, the Continue and Collections rows arrive late from Room and
are inserted at index 0 (`HomeViewModel.kt:157-162`), pushing every row down 291 or 326 px. Twelve
catalogs answer over several seconds, so this repeats.

Spec §3.7 already forbids it: "If focus is inside or below that row, the removal waits until focus
moves above it."

**The posters themselves fading.** F13 and F14. A poster that leaves a row and comes back loses its
`painted` flag (`Components.kt:677`), so the title text draws over it again; the image then arrives
from the disk cache and Coil fades it in over 190 ms (`ImageLoaderFactory.kt:69`). The memory cache
is 15% of heap (`:34`), which is a few rows' worth on this box, so walking a row twice re-triggers
it every time.

F05 is the third thing a viewer sees on this screen: in `p6-home.png` the whole 524 px hero band is
empty because the focused card is a folder, and the Play button under it does nothing.

- `WAVE2_SEARCH_CAL_SETTINGS_REPORT.md` §6.11, LEFT on Home does not always open the rail. The
  cause is `TvCardRow`'s LEFT handler: it lets the key bubble only when `focusedIndex[0] <= 0`
  (`HomeRows.kt:147-152`), and `focusedIndex` is a plain `IntArray` written by
  `onFocusChanged` on a wrapper `Box` (`:171`). When focus enters the row through `focusRestorer()`
  rather than a key press, the wrapper's callback can run after the key handler reads the value, so
  the row swallows LEFT at card 1. Fix: read the index from `listState.firstVisibleItemIndex` plus
  the focused child's own index, or write `focusedIndex` from the card's `onFocused` callback,
  which already exists and fires first.
